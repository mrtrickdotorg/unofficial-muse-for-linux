# Muse for Mac feature inventory and Linux port plan

The target is a native client for the user's existing Muse personal agent plus permissioned Linux host capabilities. No Mac relay or embedded website is required. The [full-port goal](full-port-goal.md) defines the acceptance bar; [account integration](account-integration.md) describes the current unsupported community path.

**Status convention:** implemented means code exists; verified means a named test or manual check exercised it. Offline tests, authenticated existing-session probes, fresh browser sign-in, packaged GUI checks, and local-host dispatch are separate evidence categories. Do not infer one from another.

| Same-account conversation and history | Typed community account adapter, native thread/history views and prompt dispatch | Second batch implementation; unsupported internal protocol, external dependency and explicit user session; integrated live/GUI evidence recorded separately. Both windows can start a conversation (the first message starts the session) and manage one: the Threads page's rows carry **Pin/Unpin**, **Rename**, **Archive** and **Delete**, each one `session_op` on the host with the listing read again after it, so a refusal leaves the row as it was. Delete is the one verb that asks twice: the first press arms that row in the app (`pages::thread_delete_press`), writes nothing, and the row paints "Confirm delete" (with Cancel) from the app's own arm; the second press sends the delete. A listing painted in between spends the arm, so a press aimed at a row the service has moved cannot remove what took its place. Proven on the packaged AppImage against a throwaway home (Nov 23, 2026): a conversation created in that session was renamed to "Linux thread ops", pinned (📌 in both drawer and page) and kept both across a real quit and relaunch, then archived out of the listing (10 rows → 9); the folder's own `op-timing.log` carries the three `session_op` round trips. Proven on the packaged AppImage against a fresh throwaway `XDG_CONFIG_HOME`/`XDG_DATA_HOME`/`XDG_CACHE_HOME` (Nov 23, 2026): the sheet made `…/account/del-ops`, Connect saved a link whose interpreter is the installed bridge venv **without hand-editing**, and the delete flow ran on a conversation from that session -- first press armed, second press `threads.op delete accepted=true threads=8` (9 → 8), the folder's `op-timing.log` carrying `op=session_op … ok=1 via=host`, and after a real quit and relaunch the account read 8 history rows with the row gone from drawer and page. Unread is the service's own count, never a local guess, and it moves while the app is open: the drawer and the Threads page read the listing again on the app's slow beat (8 s), so a message arriving on a conversation nobody has open badges that row without a relaunch. Proven on the packaged AppImage (Nov 23, 2026, artifact 86,108,664 B at 20:36) with a probe message sent into an unopened conversation from a second bridge process: the drawer row read "… (1 unread)" 14 s after the send and the Threads page painted the badge with its **Mark read** press. Opening a conversation clears it: `chat.mark_seen` goes out first (a row the listing already calls read costs nothing), then the same listing read repaints both surfaces -- `op=mark_seen … ok=1` in the folder's log, and `sessions.list` afterwards reported `unread_count: 0`. A launch whose saved-link connect fails no longer stays signed out: the listing beat carries the same whole account, fault-injected once with a failing interpreter wrapper (`connect settled=false`) and observed signing the window in on the next beat (`the listing beat repaired a launch with no account (Lotus)`, drawer payload at 15.7 s); a launch with no conversation in hand opens the newest one instead of painting its rows under a "New chat" header, and a new chat reads no transcript at all. Unarchive is now reachable from a row (Nov 27, 2026), and the service's own limit is why that had to be built here: `session.archive` answers `{"archived": true}`, and from that moment `sessions.list` stops returning the session -- `include_archived`, `archived` and `all` bodies answer with the same shortened list (probed Nov 25, 2026: 7 rows became 6, none archived) -- while `sessions.get` still resolves the id and reports `archived: true`. Nothing lists it, so no row could offer Unarchive. The app therefore keeps a ledger of what it archived (`apps/muse/src/archived.rs`: id and title in `archived-sessions.json` beside the account folder, bounded at 200) and paints those rows under an **Archived** header, whose menu reads Rename / Pin / **Unarchive** / Delete. Observed live after a fresh sign-in (the saved jar had expired and `api/session` answered 401; re-signed through the app's own `muse_account_login.py` into the same account folder): a scratch conversation was archived from its row's ⋯ menu, the ledger then held `[{"id":"a1f83faf…","title":"Archive proof scratch"}]`, the page painted "Archived" with that row inside it, and pressing Unarchive emptied the ledger, dropped the header, returned the row to the listing, and left `sessions.get` answering `archived: false` with `sessions.list` naming it again. That run found two defects, both fixed: painting pruned the ledger against the app's *stale* held listing -- the pre-archive one -- so archiving wrote the memory and deleted it in the same breath and the row vanished with nothing left to unarchive; painting now only merges (`archived::merge`) and only a freshly read listing sweeps (`archived::sweep`, in `pages::listed_rows`). And the native list filed archived rows under a day header ("Earlier"), now under "Archived". The React shell's Threads page carries the same Archived section with a Unarchive button under its own DOM test, but WebKitGTK drops synthetic XTEST input on this seat, so the live presses above were made in the native GTK window; the shell path rests on its test, not on a live press. |
| Shared scheduled tasks and execution history | Native schedule/run lists; delete a schedule from Linux | Second batch implementation; `tasks.list` is schedules and `tasks.runs` is executions; a schedule is deleted from the app's own Tasks page, and the React page and the native GTK rows share one app-held arm: the first press arms the row and writes nothing, the second sends the one `tasks.delete` and the page (or the native page, rebuilt) reads the listing again, which is the only proof it is gone; a listing read in between spends the arm, and a job id the held listing does not name is refused before anything reaches the wire. On the final packaged AppImage (Nov 24, 2026, 86,133,240 B at 20:41) the arming press was driven live through WebKitWebDriver: the row's label turned to "Confirm delete", the page said *nothing has been sent yet*, and the app logged `tasks.delete answered in 50us` with no service call; a `Refresh` then put the label back to `Delete` and dropped the note, proving the arm dies with the listing. The confirming press was not sent: every schedule on the account is the user's own, so deleting one is their decision — the single `tasks.delete` that press would send is covered by the adapter's unit test and the bridge's recorded route. An app-lifetime notifier now reports the account's runs (`apps/muse/src/scheduler.rs`, started once at launch, not per page and not per window visit), and it fires nothing: the pinned client's 258-route table carries `tasks.list`, `tasks.runs`, `tasks.delete` and `tasks.subscribe`, and no route that starts, triggers or retries a run, so the earlier design -- arm `next_run_at_utc`, dispatch through `tasks_run`, watch the listing for the service's own run -- was a guaranteed `bridge_failure` per due instant and was deleted on Nov 25, 2026 along with its catch-up window, its watch deadlines, its `flock` seat slot, its `scheduler-fired.json` ledger and the `MUSE_SCHEDULE_DUE_PROBE` seam. The service schedules and runs the jobs; the app reads `tasks.runs` (through the bridge's `tasks` op, which is `tasks.list` plus `tasks.runs`) every 60 s, and every 15 s while some run is `running`, and each read refreshes the Tasks rows, the Upcoming page and an open Tasks page exactly as the listing read always did. A bounded ledger of announced run ids (`$XDG_CONFIG_HOME/unofficial-muse-for-linux/notified-runs.json`, 200 ids, written atomically) makes each run news exactly once: the first launch of a seat seeds it from the account's existing history and posts nothing, a run still `running` stays out of the ledger so its result is announced when it lands, a failed read posts nothing and logs one line per failed streak, and a run the service still calls `running` thirty minutes after it came due is said once with the status it last had while its result still gets its own notification. Live on the rebuilt AppImage (Nov 25, 2026, 86,194,680 B at 08:27): the first launch logged `muse notifier: seeded 25 run id(s) from the account's existing history; nothing was announced` and wrote those ids with no notification; the polls then logged `read 25 run(s), 0 new` until the service started its own `Chaos Coordinator extraction queue drain`, when `read 25 run(s), 1 new` was followed by `muse notify: posted id=Some(10) summary="Scheduled run: Chaos Coordinator extraction queue drain"`, captured on the session bus as `Notify` from `Muse`; the next poll logged `read 25 run(s), 0 new`, so that run was not announced twice. The later polls found only their own new runs and posted ids 11-14 once each (`Chaos Coordinator extraction queue failure guard`, `Chaos Coordinator extraction queue drain`, `heartbeat`, `Hendrick.net key senders watch`); the ledger held 30 unique ids (25 seeded plus the 5 announced) and no run id was posted twice. A click is routed only for the app's own notification: the ids come from `Notify`'s one-field reply, and reading that reply as a bare `u32` failed on every call, so the app kept id 0 and any unparseable click looked like its own — both halves are fixed (the reply is read as `(u)`, a click whose parameters are not the spec's `(us)` is dropped, and the id set is no longer forgotten when the card expires, so a click from the tray minutes later still lands). On the rebuilt artifact (Nov 25, 2026, 86,182,392 B at 07:12) the run's notification was posted as id `1`, a click on id `1001` — never posted by this app — routed nothing, and the same click on id `1` logged `a notification was clicked (action="default")` and switched the window to the Tasks page. On the 08:27 artifact a synthetic `ActionInvoked` with `(uint32 1001, 'default')` -- an id this app never posted -- routed nothing, while the same signal for id 10 logged `muse notify: a notification was clicked (action="default")`, `muse notifier: a run's notification was clicked; opening Tasks` and `muse-window: the app switched this window to "tasks" at 297225ms`; the page then re-read the notifier's cache (`muse shell: tasks.snapshot answered in 154us`), so the one read still feeds the pages. The **Run now** control on a schedule row is disabled and carries the reason rather than pressing into a route that does not exist (`No run route: the service runs these schedules itself, so this page reports its runs and cannot start one.`, said once above the rows and named on the button); the route table has no create/edit/enable route either, so creation stays conversational, and the service schedules and runs the jobs |

## Safety rules

1. A folder grant covers only the selected canonical directory. No path escape or unrestricted home/shell access.
2. Local files remain read-only and separate from account linkage. Writes/moves/deletes need distinct grants and confirmations.
3. Screen/input access must use the desktop consent mechanism; unavailable APIs remain unavailable.
4. Sending a prompt is an explicit external action and may trigger the existing agent's remote capabilities. Do not auto-retry an uncertain dispatch; history confirmation proves prompt persistence, not task completion.
5. Never commit or log credentials. The current session jar is plaintext protected by private ownership/permissions (directory 0700, file 0600), not encrypted storage; keyring integration remains future work. It is feasible rather than blocked — a Secret Service (`org.freedesktop.secrets`, ksecretd) is running on this seat — but moving stored credentials into it changes the app's security posture, so it waits for an explicit decision instead of being taken on the app's initiative.
6. Existing CLI sessions are opt-in, not silently discovered/reused. Reject symlinks and insecure credentials without changing arbitrary files.
7. Keep unsupported protocol, source/license provenance, dependency trust, and service drift visible. Do not bundle external Meta-derived route/descriptors or a credential-bearing environment.
8. Future local sends/shares/purchases/deletes require fresh detail-specific approval and read-back verification. Account sign-in is not a Linux permission grant.
